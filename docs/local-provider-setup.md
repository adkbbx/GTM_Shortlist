# Local Tavily setup

Implemented and verified against the full phone/laptop suite. The user asked for a masked key-entry box rather than terminal setup. The box belongs to the trusted local workspace only. Hosted customers use the managed provider and cannot replace a service-wide key.

Three choices considered: browser storage makes a background worker depend on that browser; editing the main .env risks unrelated settings and requires restart; a separate owner-private provider database gives the API and worker one transaction boundary. Choose the third, outside Git and research/export storage. Its path appends .providers to the complete configured database filename, keeping different database paths independent.

On Windows, encrypt with current-user DPAPI, with UI forbidden and no machine-wide protection flag. On POSIX, require an owner-only regular file, mode0600; the payload is protected by permissions rather than encryption. SQLite commits leave either the previous complete key or the new complete key, including after abrupt process exit. An initial file-replacement prototype hit Windows sharing failures under concurrent readers/writers; using the existing SQLite transaction mechanism removes that custom file lifecycle. Never log, return, preload or include a key in a request-validation error. Keep a bounded tvly-prefixed token and generic failures. Hosted mode never reads this local file.

Only the loopback workspace can submit: require a matching Origin and application/json, restrict the route to local mode, bound the streamed body before parsing and keep the existing trusted-host/cross-origin protections. The local workspace is a trusted single-user interface, not an authenticated public settings service. Do not expose it on the LAN or through a public tunnel to accept secrets on a phone.

Saving config is not proof the provider accepted a key. Make no extra paid search just to test it. Explain that the next separately confirmed run uses the key; provider failures stay in the existing durable attempt journal. The worker loads the saved key between runs without changing a request already underway. Existing source reuse, attempt caps, leases and company credits remain authoritative.

Required proof: actual Windows encrypt/decrypt and a separate process reading the ciphertext; malformed/oversized/cross-origin/hosted requests leave the previous key intact and never echo input; generated public schemas/exports contain no secret value; the actual next worker receives the saved config; phone/laptop masked-entry and retry/clear states remain usable. Physical phone access still depends on a hosted deployment, whose customers do not configure global provider keys.

Provider reference: [Tavily quickstart](https://docs.tavily.com/documentation/quickstart) and [search endpoint](https://docs.tavily.com/documentation/api-reference/endpoint/search). The existing bounded adapter performs real searches after target confirmation; key entry itself performs no search.

The private file and journals are ignored by Git. It is not a portable plaintext .env export. Windows recovery requires the same OS-user protection context; reinstall/migration may require entering the key again. POSIX backups must preserve owner-only permissions. If a first interrupted save leaves unavailable configuration, retry through setup; corrupt data never gets treated as a valid key. Closing the form clears browser input, not the saved server configuration. Revoke a compromised key in Tavily and save its replacement.

Local verification: actual DPAPI encryption/decryption, separate-process reads, concurrent transactions, and child os._exit before/after commit. Two POSIX permission/symlink cases run in Linux CI rather than being claimed from Windows. See PROGRESS.md for full-suite evidence and remaining real-provider/deployment gates.

Startup loads ordinary environment settings independently of this private payload. Health reports a local_search_error with search unavailable when the payload cannot be read, so the workspace and key box remain accessible. A replacement can repair a malformed payload in an otherwise valid database. The continuous worker preserves queued work without dispatching providers while private config is unavailable; a one-shot worker reports the error and removes its heartbeat. A physically corrupt database requires operator restore/removal before another key can be saved.

Open Settings in the local header to see Company search and Research model as Configured or Not configured, plus the worker status. Click a provider's status to open its form. Configured means the required settings are present; it does not claim a successful connection test. Company search accepts a masked Tavily key. Research model accepts a trusted OpenAI-compatible Gemma endpoint, exact model ID and optional masked token. It replaces the complete saved model configuration; a blank token means no authentication. Forms never retrieve or preload saved values. After saving, the form closes and status persists on reload. The main company-entry form remains the sole research entry action. Settings is read-only in the isolated design preview and is absent from hosted accounts.

Model configuration uses a separate encrypted local_model row in the existing private database, preserving the Tavily row. It shares the same local-only origin/client, bounded JSON and secret-safe validation. Remote endpoints require HTTPS; HTTP is allowed only on localhost,127.0.0.1 or ::1. Embedded credentials, queries, fragments and malformed ports are rejected. Saving does not probe connectivity or dispatch research. Environment settings remain the fallback until a local model configuration is saved. The worker loads replacements between runs.

The local worker executes durable jobs and saves checkpoints independently of the browser. Research actions start it automatically after the command is accepted and saved, using the loopback-only POST /api/local/service/start boundary. Provider readiness is checked before queuing work. Opening Settings, loading saved results and saving provider settings do not start research. Settings shows Research service as Running or Stopped without a separate service button or terminal instructions. Paused local runs offer Resume research; startup errors preserve the saved run and its request key for retry. Starting processing can resume queued jobs and consume provider credits.

The API owns its managed worker thread, serializes concurrent startup, reuses an already-online supervised worker and signals its worker to stop during API shutdown. The durable worker honors shutdown between runs while retaining checkpoint/lease recovery for an interrupted current run. Hosted mode and the design preview reject the local startup endpoint. The8019 review service is refreshed with this behavior but remains stopped until an explicit research action. Port8018 and its existing queued run remain design-only.

## Guided model connection

Model setup starts with On this computer or Hosted provider. LM Studio and Ollama presets fill their documented OpenAI-compatible base addresses; OpenRouter fills its API base address and links to key creation. Installation/server instructions and hosted key/pricing instructions appear with the selection. Custom server addresses and manual model IDs remain available. Changing the server, address or key discards previous lookup results and model selection. Closing the form clears its secrets; saved configuration remains unchanged until Save research model.

Find available models explicitly calls local-only POST /api/local/model/models, which performs one GET to the selected server's /models resource. It performs no inference, retry, download, credential save, research creation or worker startup. No lookup occurs on page open or provider selection. The API shares the existing local-origin/client and2048-byte request boundary, validates addresses/tokens, disables redirects and environment proxies, bounds metadata at4MiB and returns at most200 safe model IDs. Gemma-labelled IDs appear first while custom aliases remain permitted. Failures return recovery instructions without response bodies or submitted credentials. Empty catalogs ask the user to install/deploy a model.

Listing a catalog does not establish inference access, credential validity for inference, structured-output compatibility or research quality. Some providers expose catalogs publicly. Those gates require separately authorized evaluation; none was performed for this change. Hosted GTM Shortlist accounts still use operator-managed providers and do not see local setup.

## Prompt profiles

The worker chooses a prompt profile from the model connection, not from local or hosted deployment. Automatic selection reads Ollama metadata once per run (GET /api/version, POST /api/show) only for loopback addresses or port 11434; it performs no inference and never probes hosted endpoints. Ollama models under 10B parameters and other on-device servers use the compact profile. Larger Ollama models and hosted endpoints use the full profile. Hosted deployments always use full. SHORTLIST_PROMPT_PROFILE=compact or full overrides the automatic choice.

Ollama's OpenAI-compatible route keeps the server's default context window (observed at 2,051 tokens) and silently drops the start of a longer prompt, which is where the instructions and schema are. Ollama connections therefore use the native /api/chat route with an explicit num_ctx (8,192 compact, 32,768 full, capped by the model's own window), a server-enforced JSON schema, temperature 0 and hidden reasoning disabled for thinking models. Page text is budgeted to fit the window; a step that cannot fit reports that the local model's context window is too small instead of dispatching.

Compact requests keep the same saved output types. Seller drafting reads 6,000 homepage characters. Campaigns propose up to three, from five competitors with 300-character excerpts. Research and verification send at most 8,000 characters of consecutive page lines ranked by target, criteria and cited passages; each excerpt is verbatim page text, so citations pass the same grounding check. Compact research assesses criteria and exclusions only: company facts and people stay empty and need a larger or hosted model. Every profile restricts criterion, exclusion and assessment identifiers to the run's own values. Compact and Ollama steps are journaled with their profile, so hosted request hashes are unchanged.

To check a local model without search calls, run `python scripts/replay_local_model.py` to list saved runs, then `python scripts/replay_local_model.py <run id>`. It reads the database read-only, replays the seller, campaign, research and verification steps on the configured on-device model, saves nothing and refuses hosted model endpoints.
